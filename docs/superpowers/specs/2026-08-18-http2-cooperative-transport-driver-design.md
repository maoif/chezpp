# HTTP/2 Cooperative Transport Driver Design

## Problem

HTTP/2 stream operations currently share one mutable nghttp2 session, socket, output buffer, and
event queue. Each stream operation independently calls `pump-http2-transport!` and derives its own
pending poll targets. This makes connection progress depend on which stream operation happens to be
stepped.

The complete `net-http` test process exposes this ownership problem. Five multiplexed requests
complete reliably, while a sixth or later request can remain pending indefinitely. The failure also
occurs over cleartext HTTP/2, so TLS teardown is not the root cause. Logging changes scheduling and
can mask the failure.

## Goals

- Give one cooperative component exclusive ownership of HTTP/2 connection progress.
- Preserve the public HTTP and `net-operation` APIs.
- Preserve serialized use of one mutable `http-client`.
- Complete sibling streams independently of the order in which callers wait for them.
- Keep queued and active cancellation local to the affected request.
- Preserve existing timeout, EOF, reset, and GOAWAY behavior.

## Non-Goals

- Thread-safe simultaneous use of one `http-client` from multiple Scheme threads.
- A background thread for each HTTP/2 connection.
- Streaming HTTP/2 request bodies.
- HTTP/2 server architecture changes.
- HTTP connection-pool redesign.
- Public API additions.

## Considered Approaches

### Transport-Owned Scheduler

The transport owns a FIFO request queue, active streams, nghttp2 progress, buffered output, and
readiness. Stream operations ask this scheduler to advance and then inspect only their own state.

This is the selected approach because it gives the shared protocol session one explicit owner and
allows input events to unlock and submit additional requests in the same advancement cycle.

### Shared Driver Operation

One `net-operation` could represent the transport and be stepped by every stream operation. This
would reuse existing lifecycle machinery, but a `net-operation` has one terminal result while an
HTTP/2 connection is long-lived and produces many independent stream results.

### Extended Pump State Machine

The current pump could gain more write, read, and event phases. This is smaller, but it retains
independent stream operations as competing owners of shared connection progress. A post-read flush
alone did not resolve the regression during diagnosis.

## Architecture

`http2-client-transport` remains internal to `(chezpp net http)` and becomes the sole owner of:

- The HTTP connection, socket or TLS session, and nghttp2 session.
- A FIFO queue of request-state records awaiting submission.
- The active request table keyed by nghttp2 stream identifier.
- The partially written output bytevector and its offset.
- Current poll readiness requirements.
- GOAWAY, closed, and reentrancy state.

An `http2-client-request-state` record represents one request independently of stream assignment.
It contains the request, finish procedure, optional response sink, optional stream identifier,
response headers and body state, terminal response or failure, deadline, and lifecycle state.

The lifecycle states are:

- `queued`: accepted by the transport but not submitted to nghttp2.
- `active`: assigned a stream identifier and present in the active table.
- `completed`: owns a complete HTTP response.
- `failed`: owns a failure value that the stream operation converts to a condition.
- `cancelled`: no longer eligible for submission or response completion.

Each public HTTP/2 stream operation is a lightweight observer of one request state. Its advance
procedure calls `advance-http2-transport!` and then maps its request state to a `net-operation`
update. It does not read, write, submit, or process nghttp2 events directly.

## Cooperative Advancement

`advance-http2-transport!` performs a bounded progress cycle while holding the transport's logical
ownership flag:

1. Submit eligible queued requests in FIFO order.
2. Flush all currently available nghttp2 output until the socket would block.
3. Read available transport input until the socket would block.
4. Feed input to nghttp2 and process every generated event.
5. Submit requests newly unblocked by received settings or stream-close events.
6. Flush frames generated by event processing and new submissions.
7. Compute the connection's current read/write poll events.

The ownership flag rejects recursive advancement as an internal invariant violation. The client is
serialized, so the design does not add mutexes or cross-thread wakeups.

When no progress is possible, every pending stream operation receives a poll target for the shared
socket. The target includes `write` whenever output is partially buffered, nghttp2 wants to write,
or queued requests may be submitted. Otherwise it requests `read`, plus error, hangup, and invalid
events in both cases.

## Request Submission

`http2-transfer/nonblocking` creates a queued request state and a corresponding stream operation.
The scheduler assigns its stream identifier only after `http2-submit-request` succeeds. Submission
failure marks that request failed without corrupting sibling state.

The internal HTTP/2 adapter will expose the peer's current
`SETTINGS_MAX_CONCURRENT_STREAMS` value. The C adapter obtains it from nghttp2's remote-settings
query and emits an internal settings event after receiving non-ACK `SETTINGS`. `(chezpp net ffi)`
binds the query, and `(chezpp net http2)` exposes it only to internal consumers. The scheduler
compares that value with its active request count before submission.

If peer settings or GOAWAY prevent a request from opening, the request remains queued or receives
the applicable terminal GOAWAY failure. The transport never drops a queued request silently. A new
peer settings event causes the scheduler to reconsider queued work during the same advancement
cycle.

## Response Processing

All nghttp2 events are processed by the scheduler:

- Header events update the matching active request state.
- Data events append to the response or write to its sink, then consume flow-control bytes.
- A normal close event completes the matching response exactly once.
- A nonzero close event fails only the matching request.
- GOAWAY records the peer's last accepted stream identifier and rejects ineligible work.

Completion removes the stream from the active table but leaves its terminal request state available
to its `net-operation`. Operation cleanup releases the response sink and removes references that are
no longer needed.

## Cancellation

Cancelling a queued request removes it from the FIFO queue and marks it `cancelled` without assigning
a stream identifier.

Cancelling an active request queues `RST_STREAM`, marks the request `cancelled`, and removes it from
normal response completion. The next scheduler advancement flushes the reset. Cancellation does not
close the transport, fail sibling streams, or overwrite completed state.

## Timeouts And Connection Failure

Each request retains the deadline captured when it was created. Scheduler advancement marks expired
queued or active requests failed; active expiry also queues `RST_STREAM`.

EOF, socket failure, TLS failure, or an unrecoverable nghttp2 error fails every queued and active
request exactly once and closes the transport. Later attempts to use that transport observe the
closed state and establish a new connection according to existing client policy.

After GOAWAY, active streams at or below the peer's last accepted stream identifier may finish.
Queued requests and streams above that identifier fail with the existing HTTP/2 GOAWAY semantics.

## Invariants

- Only `advance-http2-transport!` mutates nghttp2 transport progress.
- A request belongs to either the queue or active table, never both.
- Only active requests have stream identifiers.
- Each request reaches at most one terminal state.
- One request's cancellation or failure does not close a usable transport.
- Connection failure terminates every unfinished request exactly once.
- Poll readiness describes the transport, not an individual stream.

## Testing

The existing `net-http2-multiplexing` mat remains the primary regression. It submits ten TLS HTTP/2
requests, cancels one stream, and requires every sibling response to complete with its correct body.
It must pass repeatedly in fresh silent processes because diagnostic output changes timing.

Focused mats will additionally verify:

- More streams than one scheduler cycle can complete.
- Waiting for the last operation before earlier siblings.
- Queued cancellation before stream assignment.
- Active cancellation and reset flushing.
- GOAWAY behavior for queued and active requests.
- EOF and transport errors failing all unfinished requests.
- Equivalent cleartext and TLS HTTP/2 behavior.
- Serialized sibling stepping in different orders.

Verification requires:

- Balanced parentheses for every changed Scheme file.
- `make clean && make` from the project root.
- Repeated `make -C tests test-some TEST=net-http` runs with empty stdout and stderr captures.
- The focused protobuf and net suite from the Phase 4/5 handoff.
- Optional loader, hash-linkage, and library-linkage scripts.
- Generated binding drift and public API documentation checks.

## Compatibility

No exported procedure, record, parameter name, or documented behavior changes. The redesign is
limited to internal HTTP/2 client scheduling and its focused tests. Existing HTTP/1.1 behavior and
the experimental HTTP/2 server implementation remain unchanged.

## File Boundaries

- `chezpp/c/net/http2.c` queries the peer's current maximum concurrent-stream setting.
- `chezpp/c/nghttp2_loader.c` loads the required nghttp2 remote-settings symbol.
- `chezpp/net/ffi.ss` binds the new internal C query.
- `chezpp/net/http2.ss` wraps the query for the internal HTTP client.
- `chezpp/net/http.ss` owns request states, scheduling, cancellation, and connection failure.
- `tests/net-http.ss` contains scheduler and multiplexing regression mats.
